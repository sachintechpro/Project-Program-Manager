# QA Test Bench — User Guide

[Open Ternstone](https://ternstone-valueops-demo.onrender.com/)

## First look

Sign in as a demo persona. Scroll to the bottom of the left sidebar and choose **QA Test Bench**. On mobile, open the navigation menu and scroll to the QA entry. The page uses the existing Ternstone visual design.

The headline metrics are sourced from the **last packaged QA execution**, not generated by a fictitious test counter. The evidence includes the automated pytest JUnit output, Playwright browser UI checks against real FastAPI responses through a local bridge, controlled local ASGI load data and explicitly documented visual inspection.

## Live status versus completed tests

**Check live readiness** performs five safe, real-time in-process checks: database query, HTML, frontend script files, release evidence and insurance reference files. It does **not** execute the entire test suite or generate sustained traffic on the free Render service. It has no write effects.

**Release summary, cases and metrics** reflect the packaged local run. Read the case ID and source reference to find the exact test in the full source ZIP. A missing external environment is marked **blocked**, and an unexecuted performance requirement is **not run**.

## Signing a demonstration Go/No-Go

1. Sign in as **Tessa Reed — QA Lead** and open Test Bench.
2. Review the actual executed cases, all blocking risks and the integration/environment caveats.
3. Enter a 20+ character rationale. Choose **GO · Demo only**, **NO-GO** or **Request evidence**.
4. Switch to **Rowan Ellis — Release Manager**, review independently, and record a separate decision.
5. The page shows **GO (DEMO ONLY)** only if both reviewers explicitly record GO for the same release evidence ID. Any NO-GO overrides to NO-GO.

The server requires a signed-in role and valid CSRF token. All decisions are recorded in the audit ledger. **There is no production GO action.** The production readiness remains NO-GO until real integration, security, data durability, availability and operational evidence exists.

## Scope and general baselines

Google's Core Web Vitals good thresholds (p75) are LCP <=2.5 seconds, INP <=200 ms and CLS <=0.1. They are not automatically measured by the app. Google SRE provides examples for availability SLOs, but **99.9% is a target to set and validate**, not a guarantee from this demo.

API p95 targets shown on the Bench are proposed **local project SLOs** (900ms, 1500ms, 500ms respectively), not authoritative commercial-insurance industry averages. Local in-process latency is not representative of Render cold starts or real network conditions.

References: https://web.dev/articles/vitals and https://sre.google/sre-book/service-level-objectives/ ; OWASP API guidance: https://owasp.org/projects/api-security-project/ .

## Limitations

- Demo SQLite is ephemeral; signoffs can disappear after redeployment.
- Live GitHub/Jira/Confluence/SharePoint/OpenAI write-readback is blocked without authorized test tenants and secrets.
- Multi-day availability, DR/restore, field Web Vitals, independent penetration testing and large-scale production traffic are not verified.
- Actual commercial insurer decisions, policy transactions, financial outcomes and legal/compliance approval require real source authority, not synthetic examples.
